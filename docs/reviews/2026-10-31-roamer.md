## What forwarding and service observations can legitimately tell us

A repeated ICMP time-exceeded response correlated to a TTL-limited probe supports forwarding at the responding hop. An ARP responder tells us which MAC accepted address-resolution responsibility on the observed link. It need not be the destination device's own MAC: proxy ARP deliberately answers on behalf of other destinations. Therefore, ARP identity, device identity and subnet membership must remain separate claims. [RFC 1027](https://www.rfc-editor.org/rfc/rfc1027.html).

Controlled TTL-expiry differences can support endpoint forwarding, but cannot by themselves distinguish DNAT to a VM, a container bridge, a different physical machine, or every proxy implementation. A plain L2 bridge does not consume an IP TTL. Initial TTLs are configurable; an observed TTL of 63 alone is insufficient. A reverse proxy terminates a client connection and can hide the entire upstream path.

HTTP headers, root content, certificates, SMB names and service banners can expose address references, virtual-host names, product identity and sometimes explicitly reported prefixes. These are attributed statements from a service, not automatically live backend devices. Addresses in URLs may be examples, redirects, stale settings or unrelated dependencies. The added HTTP observer performs a bounded root GET, does not follow redirects, does not submit credentials, and records address/prefix references with their source. It does not crawl paths or change device configuration.

A container need not introduce a separate subnet: Docker host networking shares the host network namespace. Bridge networking and published ports have different semantics. These counterexamples rule out inferring a container subnet merely from a Linux application on a host with a different apparent stack. [Docker host networking](https://docs.docker.com/engine/network/drivers/host/), [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/).

## Distinguishing network relationships

| Relationship | Evidence that supports it | What remains unknown without further access |
|---|---|---|
| Routed destination | Correlated TTL expiry and destination responses, repeatable from a recorded vantage point | Remote connected subnet, full return path and router alias identity |
| Proxy ARP | A MAC answers ARP for another destination and independently demonstrated forwarding serves that destination | Whether the remote address belongs to another IP prefix or a split/extended subnet |
| Published/forwarded service | Repeated controlled TTL-expiry behaviour at a specific endpoint, or an authorised NAT mapping read | Backend address/mask unless a mapping or backend view is available |
| Reverse proxy | Application/proxy metadata or authorised configuration establishes upstream handling | Upstream transport topology and number of backend devices |
| Container or VM network | Authorised interface, bridge, namespace, virtual-switch or hypervisor inventory | Virtualisation type cannot reliably be decided from TTL, banners or OUI alone |

These are overlapping properties: proxy ARP can coexist with routing; a VM can be bridged, routed or behind NAT. A single mutually exclusive host label cannot represent all of them.

## Establishing exact prefixes without guessing

Prefer explicit address/mask or connected-prefix observations: authorised interface configuration, authenticated IP-management data, or DHCP configuration correlated to its interface and network context. RFC 8344 models interface IP addresses and prefix lengths. RFC 4292 exposes route destinations, prefix lengths and next hops, but a route can be an aggregate, default, host route or policy route. It must not automatically become a remote connected subnet. [RFC 8344](https://www.rfc-editor.org/rfc/rfc8344.html), [RFC 4292](https://www.rfc-editor.org/rfc/rfc4292.html).

Existing ICMP address-mask responses can provide explicit mask statements, but this cannot be the main modern strategy: address-mask request/reply messages are deprecated. DHCP's subnet-mask option is another explicit source, subject to attribution and freshness. [RFC 6918](https://www.rfc-editor.org/rfc/rfc6918.html), [RFC 2132](https://datatracker.ietf.org/doc/html/rfc2132#section-3.3).

A smallest CIDR covering responsive addresses is only an address-covering convenience. The scope is an authorisation boundary, not an upper bound on the real subnet. Response density, common TTLs and numeric adjacency do not establish masks. Multiple IP prefixes can share a link; one prefix can be exposed through multiple paths. If no source reveals a mask, `prefix: null` is the accurate result.

For `.139`, the next legitimate observation is its already-discovered HTTP endpoint. If that reveals only a login page or generic server, the precise missing information is a backend address/mask, connected route, forwarding mapping, or an authorised observation point on the backend. Credentials must be supplied through an approved channel; this change does not guess communities/passwords or attempt login bypass.

## Autonomous architecture and remaining capabilities

The implemented loop remains environment inspection, capability applicability, observations, inference, explicit open questions, bounded follow-ups, service enrichment, re-inference and reporting. Technique selection belongs in deterministic code; an optional reasoning component may propose observations but cannot grant scope or promote a hypothesis to fact.

The new `network_observations` report collection separates configured interface prefixes, configured routes, DHCP prefix statements, service-reported prefixes and observed/referenced addresses. Each has a stable identifier, source, evidence, claim state and relation to scope. Published-service graph nodes have no fabricated backend address. Authorisation records remain independent of observation records.

Further work is still needed for authenticated remote interface/FIB collectors, read-only virtualisation inventory adapters, temporal per-observation persistence, route-context/VRF identities, multipath-aware tracing and router alias resolution. The Windows helper firewall verifier is implemented; other operating systems need their own independently verified enforcement adapters before active execution. These capabilities are not claimed as completed here.

Relevant research cautions against constructing a single physical path from ordinary traceroute replies. Paris traceroute controls flow identifiers to reduce load-balancing artifacts; MDA-Lite explores multipath with an explicit failure-probability model. Probe should retain per-flow/per-vantage path observations rather than overwrite a hop with the last response. A flow-consistent tracing adapter must also fit the existing packet guard and independent audit. [Viger et al., traceroute measurement artifacts](https://arxiv.org/abs/0904.2733), [Vermeulen et al., MDA-Lite](https://arxiv.org/abs/1809.10070).
